# 15 中栏的占用档位

- 适用对象：想让界面出现在中栏（对话区）的插件作者。
- 效力：含 RG / AD，逐条标注。
- 本文的判据是否可自动检测：占用档位可半自动（注册的座位 id 与声明的档位是否一致）；「该占满还是该进页签」只能人工审查。

这一页回答一个一直没被回答的问题：**我不想只做浮层，我想让界面占掉中栏或者进那排页签，行不行、凭什么。** 结论先行——中栏有**三种**用法，不是两种；而且右栏不是「更大的浮层」，它是一条结构完全不同的轨道。

## 1. 中栏有三种用法

| 档位 | 怎么进去 | 一次能看到几个 | 它和当前会话的关系 |
| --- | --- | --- | --- |
| A 整页面板 | 注册一个 `main` 面板，并在左栏 `sidebar.panellist` 放一个入口图标 | 一个 | 无关；离开会话也在 |
| B 会话视图页签 | 往 `conversation.view` 注册一个会话视图 | 一个（**一次只渲染一个**） | 同一个会话的另一种呈现 |
| C 中栏内的插入点 | `conversation.input.dock` / `conversation.composer.dock` / `conversation.input.overlay`，或借道落到两侧留白带 | 与正文同时可见 | 跟着当前轮次变 |

三者不是同一个东西的三种大小，而是三种不同的关系。选错档位的代价不是「不好看」，是**功能不成立**：把需要边读正文边看的东西放进档位 B，用户就得来回切页签；把与任何会话无关的工作台塞进档位 C，用户一换会话它就没了。

## 2. 档位 A：整页面板

[官方源码] `main` 是 `keyed` / root 座位，官方用途是「按左栏条目 id 选中的中央面板」；`sidebar.panellist` 是 `list` / root 座位，官方用途是「全局面板图标」。这两个座位是同一个机制的两端：**入口图标与被选中的中栏整页面板由同一个条目 id 关联。**

[运行时实测] 干净 profile 里点左栏顶部的全局面板图标，中栏会从会话切到一个整页；「对话」不是中栏的唯一内容，只是其中的一种。

什么时候用：

- 你的界面是一块**独立工作台**（插件自己的列表、配置、报告页），和「用户此刻在和哪个会话说话」没有关系。
- 用户愿意为它离开当前会话，看完再切回来。

- `RG-MF-10`：档位 A 的内容必须在 `sidebar.panellist` 有一个入口图标，且入口图标与面板条目的 id 一致；不得只注册面板而没有回到它的入口。[本仓库建议]
- `RG-MF-11`：档位 A 的界面不得依赖当前会话状态。它可以在没有选中任何会话时渲染（`main` 是 root 作用域）。[官方源码]

> 无证据：本仓库尚未采集到第三方插件完整走通「`sidebar.panellist` 入口图标 + `main` 整页面板」的实景。上面的座位语义出自官方用途原文与干净 profile 里的官方面板，第三方路径请自行对照你的 DSH 版本复核。

## 3. 档位 B：会话视图页签

[官方源码] `conversation.view` 是 `list` / `session` 座位，官方用途是「已注册的会话目标视图，**一次渲染一个**」。会话头部那排「对话 / 轨迹 / 上下文」就是它渲染出来的，不是三个写死的页面。

「一次渲染一个」这五个字决定了谁能进档位 B：**它只能是同一份会话的另一种看法。** 正文本身永远占着其中一个位子，所以进档位 B 的代价是「用户此刻看不到正文」。

什么时候用：

- 内容是当前会话的另一种呈现：轨迹、上下文、审查、导出预览。
- 它与「对话」是互斥关系——用户看这个的时候，本来也不需要看正文。

- `RG-MF-12`：档位 B 的内容必须能回答「它与对话正文是同一份数据的两种看法吗」。答不上来就不要进 `conversation.view`。[本仓库建议]
- `RG-MF-13`：注册到 `conversation.view` 的视图不得假设自己会与正文同屏；标题、空状态、滚动条都要在整页宽度下成立。[本仓库建议]

> 无证据：官方用途写明它是注册式的 list 座位，但本仓库没有实测过「第三方注册一个会话视图之后，会话头部是否会自动多出一枚页签 chip」。在核实之前，不要把「注册即出现页签」当成已知事实写进你的 README。

## 4. 档位 C：中栏内的插入点与浮层带

中栏除了正文，还有一组随输入卡走的插入点，官方用途逐条如下：

| 座位 | 官方用途原文（译） | 它适合装什么 |
| --- | --- | --- |
| `conversation.input.dock` | 输入卡**上方**的全宽条目 | 附件、参数、预设这些「这次输入要用到的东西」 |
| `conversation.composer.dock` | 输入卡**下方**的环境条目 | 状态行、用量摘要、随会话变化的读数 |
| `conversation.input.overlay` | 渲染在常驻输入卡**内部**的浮动条目 | 补全、下拉、提示这类瞬时 UI |

再加一类：把 `conversation.input.overlay` 里的浮层绝对定位到中栏右侧那条留白带上。这条留白带**官方没有座位**（见 [区域地图](05-region-map.md) 第 5.1 节），属于借道实现。

什么时候用档位 C：

- 内容要**与正文同屏对照**，用户不希望切换视图。
- 内容**跟着当前轮次或当前输入变**，换个会话就该换一批。
- 内容可以随时消失而不影响主流程。

- `RG-MF-14`：档位 C 的常驻内容不得放进 `conversation.input.overlay`。该座位的官方用途是「输入卡内部的浮动条目」，官方在 `spec/10-frame-layout.md` 的 `FL-MF-04` 里已把它限定为瞬时 UI。要常驻就用 `conversation.input.dock` 或 `conversation.composer.dock`。[本仓库建议]
- `RG-MF-15`：借道留白带的实现必须在零宽度下退场（`RG-AD-05`），并且不能把正文挤窄——留白带的宽度是正文居中之后的余数，不是预留。[本仓库建议]

## 5. 与右栏的分界：五条结构差异

「该放中栏还是放右栏」不能靠视觉偏好回答，只能靠可测量的差别。这五条全部出自官方数据与官方源码：

| 维度 | 中栏内的档位 C | 右栏 |
| --- | --- | --- |
| 它是什么 | 中栏内部的一块余量；正文居中之后剩下的半侧留白 | **页面第 4 列**。官方措辞：一条中栏为它让出空间的轨道，或者干脆不存在 |
| 宽度从哪来 | 推导式：`floor((中栏宽 − 正文宽) / 2) − 间距 − 内缩`，**可以是 0** | 声明式：自己定宽（默认比例 0.45、下限 300px、上限 0.7 倍） |
| 谁给谁让路 | 官方没给它让步顺序，因为它不是竞争者；正文一到下限（640 / 680）它就一起消失 | 官方 `columns` 的次序写明：右栏先缩 → 再失去轨道 → 才轮到中栏跌破 400 |
| 怎么共存 | 同一个 list 槽里的多个固定层，**没有页签概念** | tab 环：多家各占一枚页签 |
| 生命周期 | 随会话内容滚动，高度就是正文的滚动区 | 每个会话一个停靠面，切换会话可以钉住原来那个 |

<!-- demo: frame-rightbar | 右栏打开与收起时的两种布局。中栏为它让出宽度，这就是「第 4 列」与「中栏内部的余量」的差别：点一下右栏，看中栏怎么让位。 -->

由此得到两条判据：

- `RG-MF-16`：内容**必须始终可达、不能随窗口变窄消失** → 它属于右栏，不属于中栏的档位 C。[本仓库建议]
- `RG-MF-17`：内容需要**跨会话常驻或跨会话钉住** → 它属于右栏。中栏的一切都随当前会话走。[本仓库建议]

## 6. 判定流程

按顺序问，第一个「是」就是答案：

1. 它离开会话依然成立，而且用户愿意为它离开当前会话？→ **档位 A**（`main` 面板 + `sidebar.panellist` 入口）。
2. 它是同一个会话的另一种看法，与正文互斥？→ **档位 B**（`conversation.view`）。
3. 它要与正文同屏，并随当前轮次或当前输入变化？→ **档位 C**（`conversation.input.dock` / `conversation.composer.dock`；只有瞬时 UI 才用 `conversation.input.overlay`）。
4. 它必须始终可达，或者要跨会话常驻？→ **右栏**（`rightbar.session` 的页签，`RG-MF-16` / `RG-MF-17`）。
5. 它是不是只影响一个设置偏好或一组设置页？→ 走 [设置页模式](../guides/20-pattern-settings.md)。
6. 全否 → 它不该待在这一屏上。

## 7. 反例：文件树与终端为什么不进中栏

文件树和终端是最常被塞进中栏右侧留白带的两种东西，两次都错，而且错的原因不同：

- **文件树**需要自己的滚动量级和层级展开，用户会长时间盯着它、来回点；它过不了「让路」这条——留白带随窗口变窄先消失，而文件树不能消失也不能缩成 0。
- **终端**需要持续存在、不能被会话切换带走；它过不了「生命周期」这条——中栏的一切都是当前会话的。

它们不是「没有位置」，是**位置在右栏**：[运行时实测] 干净 profile 的空白会话右栏开始页就有「工作区文件」「新建终端」两项宿主操作，右栏也有给文件树和文档预览用的页签内动作位（`sidebar.right.tab.files.actions`、`sidebar.right.tab.document.actions`）。想去中栏找一个位置给它们，是在解决一个不存在的问题。

## 8. 开合动效的硬约束

留白带是可折叠的：展开时它占掉中栏里的一段宽度，正文相应让位；收起时那一段宽度还回去。

- `RG-MF-18`：**占位方的宽度切换不做过渡。** 让位是一次性到位的，只有内容自己用 `transform` 与 `opacity` 进入与退出。两条理由：`MO-RC-08` 已经禁止对 `width` / `padding` 这类布局属性做动画；而一旦两侧各自过渡，它们的进度不会一致，用户看到的是边缘脱开、内容跳一下。[本仓库建议]
- `RG-RC-19`：如果确有理由让占位过程也有过渡，占位方与轨道**必须引用同一组时长与缓动变量**——把时长与曲线提成一个自定义属性，两边都引用它，不要在一边写死数值。这是对 `MO-RC-08` 的偏离，按推荐组口径在 README 写明理由。[本仓库建议]

时长与曲线的取值档位见 [40 动效](40-motion.md)。**这组数值已冻结（2026-10-06）**：展开与收起都取 **300ms**（五档里的「较大区域进入：面板、侧栏、浮层出现」），曲线取标准曲线 `cubic-bezier(0.40, 0, 0.20, 1)`；`MO-RC-03` 要求进出对称，所以「收起快一点」在这里不成立。要过渡时，把这两个值写成一组自定义属性放在占位方或轨道任意一侧的共用祖先上，两侧都引用它，不要各写一份——`B14` 判的就是这件事。降级按 `MO-RC-09`：reduced-motion 下位移与缩放归零，只保留一次透明度切换。
