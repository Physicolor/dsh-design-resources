# 80 冲突裁决

- 适用对象：多个插件占用同一座位或同一段视觉空间时的各方；以及需要提起申诉的插件作者。
- 效力：含 MF / RC / AD，逐条标注。
- 本文的判据是否可自动检测：冲突的**存在性**可以（扫描每个座位的占用者与 order 集合）；冲突的**裁决结果**不可以，需协商。

## 1. 冲突类型

| 类型 | 表现 | 可否自动发现 |
| --- | --- | --- |
| 未声明 order | entry 落在默认值 0，顺序由注册时序决定 | 可 |
| order 撞车 | 同一座位多个占用者同值 | 可 |
| single 遮蔽 | 后占用者替换先占用者，官方 UI 消失 | 可（占用者计数 >1 于 single 座位） |
| 视觉空间争抢 | 同一行控件过多、命中区被压到 <20×20 | 半自动 |
| 语义重复 | 两个插件提供同名同功能的入口或图标 | 不可 |

## 2. 实证

| 座位 | 事实 |
| --- | --- |
| `shell.overlay` | 14 个占用者，其中 13 个未声明 order，全部落在默认值 0；层级顺序由注册时序决定，不可预测 |
| `settings.section` | 11 个占用者，其中 research-cordis / dsh-market / ui-harmony 三个 order 均为 40，顺序无法解释 |
| `conversation.session.header.utilities` | 4 个占用者，order 为 -10 / -5 / 0 / 5，排布清晰 |

结论：冲突的根因不是「占用者多」，而是「未声明 order」。同一座位 11 个占用者若各自声明不同的 order，本身并不构成缺陷。

## 3. 裁决规则

- `CF-MF-01`：冲突判定只看声明与配置，不看注册时序。任何可见顺序依赖于注册时序的情形判为缺陷，责任在未声明 order 的一方。[本仓库建议]
- `CF-MF-02`：single 座位被遮蔽时，order 不参与裁决——order 对 single 无意义。被遮蔽方不得以调整 order 的方式对抗。
- `CF-MF-03`：新插件进入已有占用者的座位，发现目标 order 已被占用时必须先取空缺值（现有最大值 +10），不得复刻已有值。[本仓库建议，与 `SL-MF-05` 一致]
- `CF-RC-04`：order 撞车时的临时裁决顺序（无权威数值，本仓库建议，官方未规定）：
  1. 声明了明确区间意图（元数据／README 说明）的一方优先；
  2. 该座位占用登记表中登记时间更早的一方优先；
  3. 仍无法区分时，由后到者让位——即把冲突视为后到者未按 `CF-MF-03` 取值。
- `CF-MF-05`：视觉空间争抢（同一行控件 >6 个，或命中区被压到 <20×20）时，后到者必须收敛为菜单或折叠，不得要求先到者缩小控件。依据 [HIG]：功能不随空间变化，只改变可见量。
- `CF-RC-06`：同一区域内两个插件提供同功能入口时，后到者应把入口并入自身面板，不新增顶层级入口。[本仓库建议]

## 4. 申诉路径

1. 在插件仓库提交「座位占用登记」：座位名、类型、order、用途、截图、插件版本。
2. 对照该座位的占用集合核对是否撞车（可自动完成）。
3. 直接向占用方的仓库提 issue，引用本规范条号（例：「`CF-MF-03`，`settings.section` order 40 已被占用」）。
4. 涉及 `replaceRisk: shadows-shipped-ui` 座位且遮蔽方无关闭开关 → 上报 DSH 官方。这属于座位风险等级层面的问题，超出社区规范可裁决的范围。
5. 视觉空间争抢在同一插件内部（自己的控件互相挤）不构成社区冲突，按 20-controls.md 第 5 节自查即可。

## 5. 诚实边界

本规范不能强制任何人改代码。它能做三件事：

1. 把 order 要求变成可检测项：缺 order、值重复、single 座位多占用者，都能被脚本列出。
2. 把冲突从「看起来乱」变成「可指认的缺陷」：能点名座位、占用者与具体值。
3. 给出统一让位规则（`CF-MF-03`、`CF-RC-04`），使协商有默认解，而不是取决于谁先发声。

它不能做三件事：

- 不能改变 DSH 运行时的座位分发次序；分发行为以官方实现为准。
- 不能替官方决定哪些座位应合并、哪些应提升为 `single`。
- 不评价插件的功能价值。冲突裁决只针对座位与视觉空间，不针对功能竞争；「你的功能比我的重要」不构成占用理由。

## 6. 占用登记表字段

本规范规定字段，登记数据由本仓库维护（不在 `spec/` 目录内）：座位名、座位类型、作用域、replaceRisk、占用者 bundle 名、order、声明来源（manifest 路径）、登记时间、备注。同一座位下 order 值必须唯一；登记表生成时对重复值与缺值各输出一条告警。
