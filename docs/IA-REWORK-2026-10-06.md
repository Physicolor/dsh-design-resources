# 信息架构重做方案（2026-10-06）

## 一、为什么要重做

作者的原话：**「实际上只是看着美观，但是没办法帮助开发者直观的解决任何问题。」**

拆成三条可验证的病灶，每条都能指到具体行号。

**1. 入口跳过了「这一屏是什么」。**
`guides/00-start.md` 第 15–22 行第一张表直接问「你的内容 → 先看 → 公开座位或结构」。读者在这一刻还没有脑内画面：左栏哪几段、中栏哪几段、右栏打开之后是什么、哪一段是官方的、哪一段是插件挤进去的。要求一个还没建立画面的人选座位，他只会挑名字最像的那个。

**2. 全部文档假设「答案是一个座位」。**
`spec/11-slot-seats.md` 第 35 行「按顺序执行，任一步得出座位即停止」，第 37 行第一步就是「同类内容是否已有官方座位承载？」。`guides/30-seats-integration.md` 第 87–96 行的判定流程第一步同样是「同类内容官方是否已有座位？」。

这条假设对两处真实存在的区域不成立：

- 中栏对话区左右两侧的留白带（社区称作 rail，`dsh-widgets`、`dsh-whale-widget` 等占着它）：官方 `SlotMap` 里没有任何槽位，且第三方不能自开槽。
- `conversation.input.overlay`：官方描述是「在常驻输入卡内部显示的浮动内容」。官方没有为「中栏右侧的会话面板」给过座位，插件把它拿来当面板用。

两处都没有座位，于是流程走到第一步就无路可走，读者只能退到「最接近的那个座位」，也就是 `rightbar.session`。**这不是读者选错，是文档没有给他第二条路。**

**3. 中栏内部只有分段描述，没有占用规则。**
`spec/10-frame-layout.md` 第 22–30 行讲了中栏三段（顶部 / 对话记录 / 输入区）和各自的座位。它没有回答开发者真正要问的那个问题：**「我不想只做浮层，我想让我的界面占满中栏，或者进上面那排页签 —— 行不行？判据是什么？」**今天没有任何一篇文档回答它。

## 二、重做的方向

不是推翻目录，是**在「选座位」之前插入一层「看区域」**，并把「官方没有座位」从死角变成一条写明结论的岔路。

```
今天：  入口 → 选座位（没有座位的内容无路可走）
改后：  入口 → ① 这一屏由什么组成／哪些有官方座位  →  ② 我的内容属于哪个区域  →  ③ 选座位
                    ↑ 新增 spec/05 + guides/00 改写        ↑ 新增 spec/15 + guides/15
```

三条设计原则：

- **每一节回答一个开发者能问出口的问题。** 标题写成问题或对象（`docs/LANGUAGE.md` R11），不写成抽象名词。
- **官方没有的东西要写出来，并且写清楚它是「没有」，不是「你没找到」。** 这类位置统一标 `[本仓库建议]` 或「官方无座位，目前是社区约定」。
- **判据必须来自结构差异，不能来自审美。** 「该放中栏还是右栏」的答案只能建立在两者可测量的差别上（宽度来源、让步顺序、共存方式、生命周期）。

### 废弃

**无。** 目录本身没有错，缺的是入口那一层。废弃任何一篇都会打断已有外链与 `data/` 里的出处引用，而收益为零。

### 新增文档的写作口径

三个新 guide 都遵守既有约定：`# 标题` 取自提问、第一段用 `>` 引用作摘要、任务清单的节标题必须是 `## 读完这一页要能做什么`（`scripts/lib/i18n.mjs` 第 27–30 行的 `TASK_HEADINGS`，生成器按它把任务清单从正文里提出来）。现有 `guides/01`、`10`、`20`、`21`、`22`、`24` 用的是 `## 任务`，生成器识别不到，这几篇的 tasks 一直是空的 —— 本次顺手把这些节标题统一，属于修 bug，不改变正文。

### 接手时发现并修掉的两个既有缺陷（都不是本轮新引入的）

作者在收尾阶段指出「核对记录那种占一半、没实际内容的侧栏直接删掉，让交互示意占满宽度」，顺这条线查下去，
发现站点上**所有产品复刻类演示**其实从某一轮起就一直是坏的：

1. **复刻被套进了两层 shadow root，样式进不去。** `mountDemos` 先把演示文档挂进自己的 shadow root，
   再调用 `mountShells`，而后者又给同一个 `[data-shell]` 元素 `attachShadow` 了一次。结果
   `.sh-root` 落在演示自己那层 shadow root 够不到的地方：实测它的计算样式是
   `display: block; width: 888px`（应当是 `display: flex; width: 1570px`），三列复刻退化成一条
   3159px 高的竖排块。`website/js/app.js` 现在把复刻挂进演示自己那层 root，并把两份样式表搬进
   复刻那层；修复后实测 `.sh-root` 为 `display: flex; width: 1570px`、`--sh-scale` 生效
   （`matrix(0.565605, …)`，888px 宽的框里左栏正好 280 × 0.566 ≈ 158）、`.sh-side` 280px、
   舞台高度 571px 而不是 3159px。
2. **演示figure 左半边是「核对记录」出处卡，把演示挤成半宽。** `website/gen-site.mjs` 的
   `demoFigure()` 原本和 `componentFigure()` 一样输出「出处卡 + 演示」两栏网格；出处卡在
   `.main-inner` 的宽度下正好占掉一半，虽然它写的是来源与核验方式，但读者要的是那块界面。
   现在 `demoFigure()` 只输出演示一栏，并把所有基于 `frame-columns` 的复刻（含 `seat-map`、
   `session-tabs`、`frame-composer`、`frame-rightbar`）加进 `demo--wide`，让站点容器放宽到
   1480px。**出处信息没有丢**：`data/demo-evidence.json` 里每条演示的 `status` / `scene` /
   来源仍然由 `validateEvidence()` 在构建期强制校验，缺一条就构建失败；这一轮只是不再把
   它渲染成占半屏的卡片。组件页的 `componentFigure()` 保持原样，它的「官方 / 本仓库实现」对照
   是那一页的主要内容。

这两处之所以长期没被发现，是因为**没有任何断言在测「复刻到底有没有渲染出来」**：
`every spec carries an operable demo` 只数 `[data-inline-demo]` 容器，而逐页探针用
`shadowRoot.querySelectorAll` 只查一层，嵌套的那一层永远查不到。现在
`website/verify.mjs` 的逐页探针改成**跨 shadow 边界的深查**（并且按节点去重，否则同一批元素
会被上下两层各数一次），并新增两层断言：
`spec demo renders — 05-region-map`（五个区域必须都在）与
`spec demo replicas are mounted and fitted`（`frame-layout` 的 3 个复刻必须既挂上、又算过缩放——
复刻按 1570px 作画，靠 `DSHShell.wire` 写 `--sh-scale` 缩到容器宽度；缩放没生效时它是「挂上了但被裁掉」，肉眼像一块被切掉右边的界面）。

顺带修掉的第三个同类问题：**`sidebar-anatomy` 的复刻根本没挂上**。它不走「整篇就是复刻」那条路
（它外面还有两块图例），所以由 `mountShells` 在演示自己的 shadow root 里找 `[data-shell]`；
而上一轮刚加的守卫「在 shadow root 里的跳过」把所有演示文档里的复刻都跳过了。这个守卫现在是多余的
——`mountShellInTree` 已经按「整篇是不是复刻」在挂载期分好工——删掉之后左栏解剖图的 280 × 905 复刻
第一次真正渲染出来。
