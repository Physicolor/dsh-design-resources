# 网站文案的语言：从 Apple HIG 学来的写法

这份文档管**面向读者的说明性文案**——网站首页、为什么页、各目录页的引导句、卡片说明、空状态、实验台提示。

它不管三件事：

- `spec/*.md` 的条文。那是给人查的规范正文，术语是必要的，不按这份文档改。
- `components/*/README.md`。组件的双轨写作（README 讲判断、SPEC 讲事实）见 [WRITING.md](WRITING.md)。
- 组件自身的 SPEC 与几何来源。那里要的是可核对的数值，不是可读的散文。

一句话分工：**WRITING.md 管组件怎么分两份写，这份文档管网站上的每一句人话怎么写。**

## 来源

Apple HIG 的中文页是客户端渲染的，直接抓 HTML 只能拿到标题。正文在文档数据接口里，中文版本体现在**路径**上（`?language=zh-CN` 无效，返回的仍是英文）：

- `https://developer.apple.com/tutorials/data/cn/design/human-interface-guidelines/widgets.json`
- `https://developer.apple.com/tutorials/data/cn/design/human-interface-guidelines/buttons.json`
- `https://developer.apple.com/tutorials/data/cn/design/human-interface-guidelines/settings.json`

`primaryContentSections` 是一棵内容树：标题、段落、列表、表格、图片、代码引用都在里面，展平后即正文。下面引用的中文原句都出自这三个文件。

## 一、Apple 的语言模式

**1. 一句话摘要，然后立刻落到场景。**
页面开头是一句定义（「按钮用于发起瞬时操作。」「小组件可让用户在其他环境快速访问 App 或游戏中的重要信息和重点交互。」），但正文第一段马上换成读者认得出的东西：「例如，用户可能会在以下位置放置“天气”小组件：iPhone 和 iPad 的主屏幕和锁屏……」定义只占一句，场景占一整段。

**2. 段落 1 到 4 句，一条规则一句加粗话。**
「最佳实践」一节里，每条都是：加粗的短句 + 一到三句解释。加粗句独立成句、动词开头、主语常常省略——「平衡信息密度。」「优先提供一天中不断变化的动态信息。」「避免在 App 内镜像小组件的外观。」没有一条写成「本组件应当注意信息密度」。

**3. 判断给得干脆，并且给替代方案。**
「如果需要在工具栏中使用按钮，请使用工具栏项。」「如果要突出显示一组选项中的首选或最有可能的选项，请为该选项使用更为突出的按钮样式，并为其余选项使用较不突出的样式。」说「别这样」的时候，下一句一定接「该用哪个」。

**4. 讲理由是讲用户会怎样，不是讲规范要求。**
「如果没有按压状态，用户可能会觉得按钮无响应，进而怀疑其是否接受输入。」「呈现过多突出的按钮会增加认知负荷，需要用户花费更多时间考虑选项后才能做出选择。」理由永远落在「用户会遇到什么」，不落在「规范如此规定」。

**5. 例子是真产品、真数字。**
天气、股市、日历、播客、Safari 的自动填充面板、邮件设置的规则面板；「大多数小组件为 16 点」「将外边距设为 11 点会有不错的效果」。没有「某类场景下」「在部分情况下」这种半句话。

**6. 第二人称。**
「你可以将推送按钮配置为显示文本、符号、图标或图像」「如果你需要显示包含两行文本或较高图标的按钮」。用户统一叫「用户」，读者统一叫「你」。整篇没有「本组件」「该规范」「使用者」。

**7. 数字和标识符都不进正文的句子里。**
「使用 `full color`（全彩）渲染模式」——标识符出现时紧跟一个中文说法；再深一点的实现细节一律甩到句尾的外链：「有关开发者指南，请参阅 `padding(_:_:)`。」正文没有代码块，代码只以引用名的形式出现一次。

**8. 表格只做对照。**
用到的表全是矩阵：小组件尺寸 × 可用平台、渲染模式 × 平台、按钮形状 × 尺寸档、帮助按钮位置 × 视图样式。每张表前面都有一句「下表显示……」；表格里是名词短语，不是句子。正文叙述里不插表。

**9. 图注是并列名词短语。**
「空闲 / 悬停 / 已选择 / 不可用」「全彩 / 透明 / 色调」「未完成任务 / 已完成任务」。图注不成句，不写「这张图展示了……」——那是图本身的事。

**10. 平台差异单独成节，只写差异。**
「平台考量因素」下面按 iOS、macOS、visionOS、watchOS 分节。没有额外要求的平台直接写一句「无针对 Apple tvOS 的额外考量因素。」，不重复通用规则。同一节内部，visionOS 讲注视与形状、watchOS 讲工具栏与全宽按钮，各写各的。

**11. 过程与变更不进正文。**
版本更新放在页尾的「更改日志」表里（「2024 年 6 月 10 日 / 重新将部分指南整理到了新主题中」）。正文不会出现「本次更新了以下内容」。

**12. 没有感叹号，没有 emoji，没有「赋能」。**
通篇陈述句。语气靠具体名词撑着，不靠形容词。

## 二、可操作的写作规则

每条给一个正例（本仓库改后的写法）和一个反例（本仓库改前的写法或常见公文体）。

### R1 开头写具体场景，不写定义

第一句必须是一个设计师能指认的画面：哪里、什么情况、谁在抱怨。定义和抽象名词往后放，或者干脆不写。

- 正例：「装到第五个插件，界面就开始不像一个产品：按钮高低不一，圆角各画各的。」
- 反例：「本资源旨在为插件生态提供一套统一的设计规范层。」——读者读完不知道发生了什么。

### R2 一段 1 到 4 句，一句一个意思

超过四句就拆段；一句话里塞两个转折就拆句。首页 lede 是全文最长的一段，也只允许三句。

- 正例：「产品给了插件能跑起来的接口，却没给「按钮多大、间距多少、动效多长、图标怎么画」的共用答案。」
- 反例：「官方既提供了技术栈，也在一定程度上考虑了兼容性，但由于缺乏系统性的设计规范层，导致在实际落地过程中出现了一系列问题。」——三个转折挤在一句里。

### R3 判断句写成「想要 X 用它；想要 Y 改用 Z」

给判断就要给替代方案。读者要知道下一步做什么，而不只是“这样不对”。

- 正例：「先找意思最对得上的 list 位置；都不合适，再考虑 single；会盖住官方界面的那些，放到最后再考虑。」
- 反例：「应结合实际情况选择合适的座位类型。」——等于没说。

### R4 讲取舍用「加粗主张 + 一到三句解释」，解释讲用户会怎样

主张句短、动词开头、独立成句；解释落到用户身上，不落到规范条款上。

- 正例：「**同一个位置上的插件顺序，刷新一次可能就变了。** 能挂多个插件的位置按 order 排先后，但没人规定该填几。默认值是 0，于是谁先加载谁就排前面——用户看到的是随机的上下关系，而不是谁更重要。」
- 反例：「**顺序声明应当被显式指定。** 未指定 order 时注册时序将决定渲染顺序，这违反了可预测性原则。」——第二句在讲规范自己，不在讲用户。

### R5 第二人称，用户叫「用户」

对读者说「你」「你的插件」，对界面里的人说「用户」。禁止「本组件」「该规范」「使用者」「笔者」。

- 正例：「自己画图标时，让它和旁边图标的粗细、留白保持一致。」
- 反例：「自绘图标应当与相邻图标保持视觉重量的一致性。」

### R6 表格只用于对照

表格存在的唯一理由是「两三个维度交叉查」。表头是维度名（平台 / 尺寸 / 场景），单元格是名词短语。凡是能写成一句话的，不要做成表；凡是需要读成一整句话的，也不要做成表。

- 正例：座位表（位置 × 类型 × 作用域 × 会不会盖住官方界面）、令牌表（令牌 × 浅色 × 深色）。
- 反例：把「官方没有做什么」做成五行的表——那是清单，不是对照。

### R7 数字保留，但必须紧跟一句「所以呢」；代码不进正文

可核实的数字是这份资源的信用，删掉可惜。但数字后面要有一句人话说明它意味着什么。标识符、CSS 变量、`px`/`ms` 这类写法不进正文句子，进表格、进代码块、进 `spec/`。

- 正例：「官方界面的 shell.overlay 位置上有 14 个插件，其中 13 个没有说明自己该排第几。系统按默认值 0 处理，顺序于是由加载先后决定——同一台机器刷新一次，可能就换了个样子。」
- 反例：「`shell.overlay`：14 个占用者，其中 13 个未声明 `order`，默认值 0，注册时序决定层级。」——数字全在，但读者不知道这意味着什么。
- 反例：「用法：`color: var(--dsw-alias-label-primary)`。」——这句该出现在令牌表的说明里，不该出现在引导句里。

### R8 禁词表

下面这些词只有内部人懂，或者带着公文腔。左边的问题不是“太专业”，是“读者要翻译一遍才能用”。

| 不要写 | 改成 |
| --- | --- |
| 本组件、该组件、该规范、本规范 | 它、这个组件、这份规范（或者直接省略主语） |
| 应当、必须、需要（作为要求时） | 写成动作：「让整行都能点」「别把它降级成次级样式」 |
| 生态、生态位 | 说清是谁和谁：插件作者、插件市场、装了很多插件的界面 |
| 规范层、赋能、闭环、抓手、组合拳、心智、链路 | 删掉，改写成具体的那件事 |
| 兼容、对齐（抽象用法）、落地 | 能装进来、看起来一致、真的做出来 |
| 契约、契约层 | 约定、规矩、说好的做法 |
| 遮蔽风险、replaceRisk | 会不会盖住官方界面 |
| 语义 token、控件原语 | 有名字的颜色和尺寸、产品里已有的按钮和开关 |
| 不可预测、非确定性 | 刷新一次可能就变了 / 谁先加载谁在上面 |

### R9 讲「缺什么」时写现象，不写条文清单

「没有 X 规范」是清单腔，读完没有画面。改成「用户会遇到什么」，一句现象加一到两句为什么。

- 正例：「两个插件都想把按钮放在侧栏底部，谁在上面全看谁先加载。」（后面接：该占多大、跟会话区怎么分没有共用答案。）
- 反例：「没有布局规范：插件该占用哪个区域、占多大、与会话区怎么协调，没有条文。」——「没有条文」是对着规范说的，不是对着读者说的。

### R10 专有名词第一次出现给半句解释

座位、令牌、order、key 这些词在这个产品里是术语，读者未必知道。第一次出现时用一个从句交代，之后可以直接用。

- 正例：「能挂多个插件的位置按 order 排先后，但没人规定该填几。」
- 反例：「list 座位需要声明 order。」——两个术语叠在一起，读者卡住。

### R11 标题写成对象或问题，不写成抽象名词

标题是读者决定要不要继续读的唯一线索。

- 正例：「为什么插件看起来不像一个产品」「这个仓库不做什么」
- 反例：「设计规范层的必要性论证」

### R12 图注、表头、徽标用名词短语

这些位置的文字不承担叙述功能，承担指认功能。写「会不会盖住官方界面」，不写「该位置在被占用时是否会导致官方界面被替换」。

### R13 差异单独成节，只写差异

平台、环境、场景之间的差别集中写；相同的话不重复第二遍。没有差异就写一句「没有额外要求」，不要为了对称硬凑。

### R14 不写过程叙述

不提「本次改造」「我们重新梳理了」，也不解释文档自己的结构（「下面分三层说清」只在真的帮读者定位时用一次）。读者只关心他要做什么。

## 三、人机话 → 人话

下面每一行的“改前”都是本仓库真实出现过的句子（`language/zh.json` 与 `website/js/app.js`），改后是这一轮采用的版本。

| 改前 | 改后 |
| --- | --- |
| 一句话：官方给了插件能跑起来的技术栈，没有给插件看起来一致的设计规范。 | 插件单独看都不算差，放在一起却不像一套东西。原因不复杂：能装进来的接口有了，装进去之后该长什么样，没有人给过统一答案。 |
| 官方兼容了技术栈，却没有兼容设计规范——这就是这个仓库存在的原因。 | 插件能装进来，却装不成一个样子——这就是这个仓库存在的原因。 |
| 一套完整的语义 token：颜色、层级、状态都有官方取值。 | 一套现成的颜色和尺寸取值：颜色、字号、圆角、间距、层级，浅色深色都有。 |

| 每个组件都是零依赖的 React 实现，只使用官方令牌，并附上几何来源与使用时机。复制即可用。 | 每个组件都是独立的 React 实现，只用官方令牌，并写明尺寸出处与什么时候该用它。拿走就能用。 |
| 75 个图标，全部从产品自身的客户端包提取，路径数据原样保留。 | 75 个图标，全部从产品里原样提取，形状没有改过。 |
| 座位是 list 类型时……（原文：list — 多插件按 order 升序排列） | list — 可以挂很多个，按 order 从小到大排。 |
| 规范里的时长不该只是纸面数字——它应当能当场比较。 | 时长写在纸上没有感觉，摆在一起比一比：350 毫秒和 100 毫秒的差别，看一眼比读十行字清楚。 |

## 四、改稿时的自检

改完 `language/*.json` 或 `website/js/app.js` 里的句子，按顺序问四遍：

1. **第一句有没有画面？** 没有具体的人、位置或动作，就重写。
2. **删掉形容词还剩什么？** 只剩「一致」「规范」「体系」这类词的句子，说明它没在说事。
3. **这句能不能被 grep 出来？** 逐条搜禁词：

```sh
grep -nE '生态|赋能|闭环|抓手|心智|链路|契约|规范层|遮蔽风险|语义 token|控件原语|本组件|该组件|本规范|应当|必须' language/zh.json
grep -nE 'ecosystem|empower|synerg|paradigm|leverage|holistic|robust solution|seamless|contract' language/en.json
```

4. **英文是不是从中文直译的？** 英文版按英语的语序重写一遍，不逐字对应；两版的句子数可以不一样，语气要一样。

改完必须重跑生成器与验证：

```sh
node website/gen-site.mjs
node website/verify.mjs
```

`language/*.json` 会被 `gen-site.mjs` 内联进 `website/js/data.js`，不重跑生成器，页面上的文案不会变。
